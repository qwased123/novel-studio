# Novel Memory System 项目总说明

## 一句话定义

Novel Memory System 是一个面向 DeepSeek Harness（DSH）的小说写作协作插件。它让 DSH 内的 AI 通过多个职责明确的写作子代理完成小说任务，并用可追溯的叙事记忆、证据和冲突闸门约束最终结果。

它不是一个独立运行的通用写作网站，也不是一个试图用单个模型完成所有工作的聊天应用。

## 当前宿主范围

当前只适配 DeepSeek Harness。

其他 Harness、通用 Agent 平台、多用户 SaaS 和独立部署形态暂不属于当前目标。Fastify API 和 Web 评测台保留为本地调试、回归测试和数据检查入口，最终用户工作流应由 DSH 插件承载。

## 为什么使用子代理

不同模型在小说任务中的优势不同：

- 有些模型擅长长文本文笔、语气和场景表现，但事实推理和连续性较弱。
- 有些模型擅长规划、分析、检索和冲突判断，但正文表达不够自然。
- 有些模型适合快速生成候选，有些模型适合慢速审阅。

因此系统不追求一个模型通吃所有环节，而是把写作任务拆给职责明确的子代理，并由 DSH 主代理负责编排。

子代理还有第二个作用：控制上下文成本。上下文窗口有限且昂贵，不应把整部小说、所有历史对话和所有中间过程反复塞给每一个模型。每个子代理只接收完成自己任务所需的最小上下文，并返回结构化结果或短文本产物。

## 目标工作流

```text
用户在 DSH 中提出小说任务
  -> DSH 主代理拆解任务
  -> 规划子代理：确定场景目标、约束和待解决问题
  -> 记忆检索：按意图提取硬约束、世界状态、角色认知、伏笔和证据
  -> 研究/连续性子代理：处理时间线、因果、人物状态和冲突
  -> 写作子代理：生成正文候选
  -> 编辑/风格子代理：优化文笔，但不得擅自改变事实
  -> 审校子代理：检查连续性、证据和任务要求
  -> 提交到 Memory System
  -> 无冲突：进入正式记忆
  -> 有冲突：阻断并请求用户裁决
```

子代理不是平行地共享全部上下文，而是通过明确的任务输入和结构化产物协作。例如：

```text
规划代理 -> ScenePlan
检索服务 -> ContextPack
研究代理 -> ContinuityReport
写作代理 -> Draft
编辑代理 -> EditedDraft
审校代理 -> ReviewReport
记忆内核 -> Submission / Conflict / Canon
```

## 建议的子代理职责

### 规划代理

把用户的自然语言要求拆成场景目标、角色、视角、时间、地点、必须保持的约束和待确认问题。它负责计划，不负责直接写入正式记忆。

### 检索与研究代理

根据当前任务调用记忆检索，整理时间线、因果关系、角色已知信息、世界规则、开放伏笔和争议证据。它不能把推测伪装成正式事实。

### 写作代理

根据 `ScenePlan`、`ContextPack` 和用户要求生成正文候选。它可以发挥文笔，但不能绕过记忆系统直接修改 Canon。

### 连续性审校代理

检查新正文是否违反时间线、人物状态、空间关系、世界规则、认知域或伏笔生命周期。它输出报告和候选修订，不自动裁决冲突。

### 风格编辑代理

只处理语言、节奏、视角、语气和段落表现。默认不得改变已确认事实、事件顺序、角色认知和伏笔状态；如必须改动，应显式标记变更。

### 记忆审查代理

对正文中的候选记忆进行抽取和冲突复核，但它的结果仍然只是候选。正式 Canon 只能由 Memory System 根据证据和用户裁决写入。

## 上下文预算原则

1. 主代理只保留任务状态和子代理结果，不保留所有中间推理。
2. 每个子代理只接收与其职责相关的 `ContextPack`。
3. 原文通过 evidence span 引用，不重复传递整篇文档。
4. 检索必须有意图和 token budget，不能无边界返回全部记忆。
5. 子代理输出优先使用结构化 JSON、短报告和明确引用。
6. 失败、冲突和不确定性必须显式返回，不能用长篇解释掩盖缺失证据。
7. 风格编辑不能成为事实修改的后门。

## 权威边界

正式原文、用户明确裁决和已确认的 Canon 是权威。

以下内容都是可重建或可被否决的派生数据：

- AI 抽取候选
- 子代理计划和报告
- 实体和关系图谱
- 摘要
- Embedding
- 检索排序
- 风格改写建议

任何子代理都不能直接覆盖正式事实。冲突必须进入 `blocked` 状态，等待用户选择共存、重分类、retcon 或拒绝提交。

## DSH 插件边界

插件适配层负责把 DSH 的会话、任务和子代理机制连接到记忆内核，核心服务本身不应绑定 DSH 内部实现。

计划中的 DSH 插件能力包括：

```text
novel_memory.open_project
novel_memory.retrieve_context
novel_memory.submit_source
novel_memory.review_submission
novel_memory.list_conflicts
novel_memory.resolve_conflict
novel_memory.audit_project
```

最小可用插件首先实现：

1. `retrieve_context`：让 DSH AI 在写作前获取受预算约束的叙事上下文。
2. `submit_source`：让 DSH AI 把设定、正文或大纲提交为候选来源，而不是直接写 Canon。
3. `review_submission`：触发抽取、冲突检测和正式化流程。
4. `resolve_conflict`：把用户明确裁决传回记忆内核。

Fastify API 和 Web 评测台可以继续用于本地验证，但不是 DSH 插件的替代品。

## 当前非目标

- 适配其他 Harness 或通用 Agent 平台
- 做成独立写作 SaaS
- 让单个模型负责规划、写作、审校和记忆管理全部工作
- 让 AI 自动决定冲突中的哪条剧情为真
- 多用户权限和生产级协作
- 复杂文档格式导入导出
- 在没有用户确认的情况下自动 retcon 正式记忆

## 当前阶段

当前仓库已经完成本地记忆内核的最小闭环：项目、来源提交、候选记忆、证据校验、冲突阻断、用户裁决、检索、Embedding 降级、异步 review worker、审计和 Web 评测台。

下一阶段不是继续扩展独立 Web，而是检查 DSH 的插件扩展点并完成最小适配层，让 DSH AI 能够调用 `retrieve_context` 和 `submit_source`，再逐步接入子代理编排。

## 命名决定

暂不立即重命名仓库或 npm package。

`Novel Memory System` 仍然准确描述核心内核，且当前代码、README、数据库和提交都已经使用这个名称。为了反映新的宿主定位，产品副标题统一使用：

> Novel Memory System：面向 DeepSeek Harness 的小说写作记忆与子代理协作插件

当 DSH 插件适配层稳定后，再根据 DSH 的插件命名规范决定是否将仓库重命名为类似 `dsh-novel-memory`。在适配层尚未落地前改名，会制造无收益的路径、包名和文档迁移成本。
